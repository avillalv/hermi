# iOS builds on CI (no Mac)

The owner has no Mac, and iOS builds need macOS and Xcode. So every iOS build runs on a GitHub-hosted macOS runner.
The repo is public, and standard GitHub-hosted runners, macOS included, are free for public repos. That is the
reason the repo stays public. (If it ever goes private, macOS minutes bill at 10 times the Linux rate.)

The app is a Capacitor shell (`apps/ios`, bundle id `world.hermi.ios`) around the web bundle, with no `server.url`.
The tickets are WF-080 (shell, signing and CI) and WF-101 (the TestFlight pipeline). `02-architecture.md` section 10
defines `.github/workflows/ios.yml`. It runs on a tag `ios-*` or by hand, and nothing else triggers it.

## The workflow

| Workflow | Trigger | What it does | Needs |
|---|---|---|---|
| `ios.yml` | Tag `ios-*`, or manual dispatch (`workflow_dispatch`, a button in the Actions tab) | `npm run build`, `cap sync ios`, archive, sign through Apple's cloud signing, upload to TestFlight, upload dSYMs and source maps to Sentry | An App Store Connect API key in GitHub Actions secrets |

**A proposal for WF-080 to decide, not in 02.** An unsigned simulator build on pull requests that touch `apps/ios`,
`apps/web` or the Capacitor config: `npm run build`, `cap sync ios`, then `xcodebuild` for the simulator SDK with
code signing off. It would prove the shell still compiles and needs no secret. It would not be a required check, so
`main` stays green when it is slow or a runner is busy. If WF-080 adds it, the same pull request updates 02 section
10 and adds a `DECISIONS.md` row.

Cloud signing means no certificate or provisioning profile is stored. The job signs with an **App Store Connect API
key with the Admin role** (Admin is what lets Apple manage the distribution certificate for you). Store these as
GitHub Actions secrets, with the names the workflow settles on (WF-101):

- the key id, the issuer id, and the contents of the `.p8` private key
- `SENTRY_AUTH_TOKEN` for the dSYM and source map upload

Never commit a `.p8`, `.p12` or `.mobileprovision` (all three are in `.gitignore`).

## If the iOS project cannot be generated on Windows

`apps/ios` is generated by Capacitor and then committed. If `cap add ios` does not complete on Windows (CocoaPods and
Xcode are macOS tools), generate it in a macOS job instead: run it there, upload the result as a workflow artifact,
download the artifact and commit it. After that the project is ordinary files, and later changes are plain edits. Do
this once, in WF-080.

## Owner steps, in order

The ordered list is in `app-buildout/prompts/HUMAN_TASKS.md`. Each step unblocks the next.

1. **Apple Developer Program.** $99 a year. Start first: enrollment can take days.
2. **Bundle id.** Register `world.hermi.ios` with Push Notifications, Associated Domains, Sign in with Apple,
   In-App Purchase and App Attest (the WF-080 list).
3. **App Store Connect app record** for that bundle id.
4. **App Store Connect API key** with the Admin role. Add it to GitHub Actions secrets.
5. **APNs key**, then `APNS_KEY_ID`, `APNS_TEAM_ID` and `APNS_PRIVATE_KEY` in the staging and production env groups.
6. **Sign in with Apple key**, then `APPLE_SIGNIN_KEY_ID` and `APPLE_SIGNIN_PRIVATE_KEY` in the same groups.
7. **RevenueCat.** Create the project, connect App Store Connect, create the products from `07-monetization-spec.md`,
   and set `VITE_REVENUECAT_KEY_IOS`, `REVENUECAT_API_KEY` and `REVENUECAT_WEBHOOK_SECRET`.
8. **TestFlight testers.** Internal testers first (App Store Connect users), then the external beta.

The variables are in `knowledge/env-and-accounts.md`.

## What the autopilot can and cannot do

The autopilot writes the Capacitor and Swift code and the `ios.yml` workflow, but it cannot run the app on a device
or in App Store Connect. Device and account criteria in WF-080 to WF-089 and the TestFlight steps are owner
verification pending: each becomes a row in `app-buildout/prompts/HUMAN_TASKS.md` and stays Open until a signed build
is on your phone. Never a status in `PROGRESS.md`: the prompt's row still reads `Done (#<pr>)`. Prompts 16, 21 and 24
skip the Xcode and pod steps on Windows.

## Testing on a phone

A phone cannot reach your PC's loopback, and the local AI provider (`claude_cli`) answers only to loopback, so a
phone build against your PC gets no AI. Point the iOS build at the staging deployment, which runs
`AI_PROVIDER=anthropic_api` and so needs an `ANTHROPIC_API_KEY` with a spend limit
(`knowledge/ai-provider-claude-cli.md`, "Switching to the API for production"). Opening a tunnel to your PC to work
around this would let other people use your subscription, which the guard exists to prevent.
